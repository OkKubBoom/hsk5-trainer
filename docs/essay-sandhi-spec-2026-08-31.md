## 1.3 เกณฑ์ตรวจ — กี่ด้าน ด้านละกี่คะแนน

### 1.3.1 คำตอบตรงๆ: **ไม่ได้แบ่งเป็นด้าน แบ่งเป็นช่วง 4 ระดับ**

โครงคะแนนทางการ 书写 = 完成句子 8×5 = 40 + 写短文 2×**30** = 60 → รวม 100
ช่วง: `0分` / `低档分` / `中档分` / `高档分`

**แหล่ง:** `https://www.chinesetest.cn/userfiles/file/HSK-pingfen.pdf` (โดเมนทางการ 汉办) และ `https://www.chinesetest.cn/userfiles/file/dagang/HSK5.pdf` หน้า 3-4 — สองบทบาทดาวน์โหลดและแกะข้อความเองแยกกัน ได้ผลตรงกันทุกตัวอักษร

| ช่วง | ข้อ 99 (คำ 5 คำ) | ข้อ 100 (รูปภาพ) |
|---|---|---|
| 0分 | 空白 | 空白 |
| 低档分 | 未全部使用5个词语，内容不连贯，有语法错误；有较多错别字 | 内容与图片相关性不大；内容不连贯，有语法错误；有较多错别字 |
| 中档分 | 内容连贯且合逻辑，有语法错误；…有少量错别字；…篇幅不够 | 内容与图片相关且合逻辑，有语法错误；…有少量错别字；篇幅不够 |
| 高档分 | 5个词语全部使用，无错别字，无语法错误，内容丰富、连贯且合逻辑 | 内容与图片相关，无错别字，无语法错误，内容丰富、连贯且合逻辑 |

⚠️ **高档 บังคับ 无错别字 พร้อมกับ 无语法错误** — ผิดจุดเดียวตกลงมา 中档 ทันที ห้ามให้ AI ใจอ่อน

⚠️ **หาไม่เจอ: แต่ละช่วงคือกี่คะแนนจาก 30** ไม่มีเอกสารทางการฉบับใดระบุ และเอกสารเดียวกันเขียนว่า「首先，将评分员所给分数转换为标准分」→ **ห้ามแสดงตัวเลข /30 ว่าเป็นคะแนนสอบจริง** ถ้าต้องมีตัวเลขเพื่อทำกราฟ ให้ใช้ 高档 24-30 / 中档 12-23 / 低档 1-11 / 0 แล้วติดป้าย ✱✱✱ ว่าเป็นการประมาณของระบบ

📌 **สิ่งที่ AI ห้ามตัดสิน — มีหลักฐานทางการตรงๆ** เอกสารเขียนท้ายข้อ 100 ว่า「考生如果侧重议论，也不会影响其成绩。因为评分员关注的是汉语表达的规范与流畅，而非立意、见识的高下」
→ ห้ามติว่า “เนื้อหาตื้น” “ควรมีมุมมองลึกกว่านี้” และห้ามบังคับว่าต้องเขียนแนวบรรยายหรือแนวอภิปราย

### 1.3.2 สถาปัตยกรรม 3 ชั้น — อย่าถามโมเดลว่า “ให้กี่คะแนน”

**ชั้น 1 — Python ล้วน ห้ามให้โมเดลทำ**
```python
char_count   = len(re.findall(r'[\u4e00-\u9fff]', text))   # LLM นับตัวอักษรผิดประจำ
is_blank     = char_count == 0
length_ok    = char_count >= 80
missing      = [w for w in required_words if w not in text]  # ข้อ 99 เท่านั้น
```

**ชั้น 2 — Claude รายงานข้อสังเกต ไม่ให้คะแนน** (โครง JSON ข้อ 1.4)

**ชั้น 3 — Python ตัดสิน band**

### 1.3.3 อัลกอริทึมตัดสิน band — **แก้บั๊ก 3 จุดที่ผู้แย้งจับได้แล้ว**

```python
BAND_ORDER = {"zero": 0, "low": 1, "mid": 2, "high": 3}

sure = [i for i in issues if i["certainty"] == "sure"]
typo_count = len([i for i in sure if i["kind"].startswith("typo")])
gram_count = len([i for i in sure if i["kind"].startswith("grammar")])
task_ok    = (not missing) if task_no == 99 else bool(image_relevant)

if is_blank:
    band = "zero"
elif (not task_ok) or (not coherent) or typo_count >= 3:      # ← ดูหมายเหตุบั๊ก 2
    band = "low"
elif task_ok and typo_count == 0 and gram_count == 0 \
     and coherent and content_rich:
    band = "high"
else:
    band = "mid"

# บั๊ก 1 ที่แก้แล้ว: 篇幅不够 ระบุอยู่ในเกณฑ์ 中档 ของทั้งสองข้อ
# ถ้าไม่มีบรรทัดนี้ เรียงความ 40 字 ที่ไม่มีข้อผิดจะได้ 高档 ซึ่งขัดกับตัวบท
if not length_ok and band == "high":
    band = "mid"
```

**หมายเหตุที่ต้องเขียนกำกับในโค้ดและบนหน้าจอ — ห้ามอ้างว่าชั้นนี้ “ทางการ 100%”:**

- **บั๊ก 2 (แก้ไม่ได้ ต้องติดป้ายแทน):** ต้นฉบับข้อ 99 เขียน「未全部使用5个词语，内容不连贯，有语法错误；有较多错别字」จุลภาคคั่นภายในเงื่อนไขเดียว อัฒภาคคั่นระหว่างเงื่อนไข อ่านตามตัวบทได้ว่าต้องเข้าครบทั้ง 3 อย่างพร้อมกัน ไม่ใช่ OR แยกกัน โค้ดข้างบนใช้ OR ซึ่งเข้มกว่าตัวบท → **ต้องคอมเมนต์ในโค้ดว่า “นี่คือการตีความ ไม่ใช่ตัวบท” และหน้าผลต้องเขียนกำกับเมื่อได้ 低档 จากเหตุ “ใช้คำไม่ครบ” เพียงอย่างเดียว**
- **เกณฑ์ `typo_count >= 3` = 较多** ยืมมาจากหัวข้อ 完成句子/看图造句 ในเอกสารฉบับเดียวกัน หัวข้อ 写短文 เขียนแค่「较多」ไม่ระบุตัวเลข → **เป็นการอนุมาน ติดป้าย**

## 1.4 โครง JSON ที่ให้ Claude ตอบกลับ

Pydantic model ใน `core/essay_grader.py` — ต้องหล่อให้ save ลง `core/models/practice.py:305-317` ได้ตรงๆ ด้วย `model_dump()`

```python
class Issue(BaseModel):
    span: str        # ข้อความรอบจุดผิด คัดจากงานเขียนตรงตัว ห้ามดัดแปลง
    wrong: str       # ส่วนที่ผิด
    right: str       # ส่วนเดิมที่แก้ให้ถูกแล้ว
    why_th: str      # อธิบายเป็นภาษาไทยว่าผิดเพราะอะไร ยกกฎให้ชัด
    kind: str        # ดูรายการค่าด้านล่าง
    certainty: str   # "sure" | "unsure"

class EssayObservation(BaseModel):
    coherent_logical: bool          # 内容连贯且合逻辑
    image_relevant: bool | None     # ข้อ 100 เท่านั้น · ข้อ 99 = None
    content_rich: bool              # 内容丰富 (ใช้แยกขอบบนของ 高档)
    issues: list[Issue]
    suggestions_th: list[str]       # “เขียนให้ดีกว่านี้ได้” — ไม่นับเป็นข้อผิด
    strengths_th: list[str]         # 1-3 ข้อ
    next_step_th: str               # สิ่งเดียวที่ควรฝึกต่อ
```

ค่าที่รับได้ของ `kind` (ขึ้นต้นด้วย `typo` / `grammar` เพราะชั้น 3 นับจาก prefix):
`typo_homophone` · `typo_form` · `grammar_order` · `grammar_missing` · `grammar_extra` · `grammar_wrong_word` · `grammar_de_particle` · `grammar_ba_bei` · `grammar_measure_word` · `grammar_separable_verb` · `collocation` · `punctuation`

> `grammar_order` (错序-定语) คือข้อผิดอันดับหนึ่งของผู้เรียนไทย เพราะไทยวางส่วนขยายหลังคำหลัก จีนวางหน้า — งานวิจัยเรื่องนี้อ้างได้แค่บทคัดย่อ (`https://www.hanspub.org/journal/paperinformation?paperid=64691`) **ไม่มีตัวเลขความถี่ยืนยัน ห้ามเขียนในเอกสารว่ารู้สัดส่วน**

**สิ่งที่เก็บลง `WritingFeedback.scores` (เปลี่ยนโครงเดิมทิ้ง):**
```json
{"band":"mid","task_ok":true,"typo_count":1,"grammar_errors":2,
 "coherent":true,"length_ok":true,"content_rich":false,
 "char_count":96,"estimated_30":18,"estimate_is_ai":true,
 "band_rule_note":"เกณฑ์ 低档 บางส่วนเป็นการตีความ ไม่ใช่ตัวบท",
 "standard":"2.0","task_no":99}
```
`WritingFeedback.issues` เก็บ `[Issue...]` ตามโครงข้างบน · `total_100` เก็บ `estimated_30 * 100 // 30` **หรือปล่อย 0 แล้วเลิกใช้** (ตัวเลขนี้ไม่มีความหมายทางการ — ตัดสินใจตอนเขียน ให้เลือกอย่างเดียวและอย่าโชว์สองตัวเลขให้ผู้เรียนสับสน)

**กฎที่ต้องเขียนลงพรอมต์ตรงๆ:**
1. ห้ามตัดสินคุณภาพความคิด/ความลึกซึ้ง/มุมมอง — อ้างหมายเหตุ 汉办 ที่ยกไว้ในข้อ 1.3.1
2. ห้ามนับเป็นข้อผิดถ้าประโยคถูกอยู่แล้วแต่ไม่ถูกใจ — ไปช่อง `suggestions_th`
3. ห้ามตัดสินว่าเนื้อหาจริงหรือแต่ง ผู้เรียนแต่งเรื่องได้
4. ไม่มั่นใจให้ใส่ `certainty: "unsure"` แทนการฟันธง (`unsure` ไม่ถูกนับในชั้น 3)
5. ห้ามนับจำนวนตัวอักษร Python ทำแล้ว
6. คำอธิบายทุกบรรทัดเป็นภาษาไทย ยกตัวอย่างประโยคจีนได้
7. `span`/`wrong` ต้องคัดจากงานเขียนตรงตัว ห้ามเรียบเรียงใหม่

## 1.5 โมเดล · ค่าใช้จ่าย

**โมเดล: `claude-opus-5`**
เหตุผล: งานคือชี้ว่า *ผิดเพราะอะไร* ตาม D8 ต้องแยก 语序ผิด vs 搭配ผิด vs 离合词แยกผิด — ถ้าคำอธิบายผิด น้องจำผิดไปสอบ ซึ่งแย่กว่าไม่มีระบบตรวจ

**ราคาทางการ (ยืนยันสองบทบาทแยกกันจาก `https://platform.claude.com/docs/en/about-claude/pricing`):** Opus 5 = **$5 / MTok in · $25 / MTok out**

| | ต่อครั้ง | รวมถึงวันสอบ |
|---|---|---|
| ตัวเลขที่วิศวกรเสนอเดิม (1,500 in / 800 out, 68 วัน) | $0.0275 | **$7.48 — ถูกแย้ง ห้ามใช้เป็นงบ** |

ตัวตั้งต้นที่ตัวเลขเดิมพลาด (ทั้ง 3 ข้อยืนยันแล้ว):
1. **โทเคนไนเซอร์ใหม่ +30%** — หน้าราคาระบุว่ารุ่น 4.7 ขึ้นไปใช้โทเคนไนเซอร์ใหม่ กินโทเคนมากขึ้น ~30% กับข้อความเดิม
2. **จำนวนวันผิด** — `config/settings.py:137` ตั้ง `TARGET_EXAM_DATE` ค่าตั้งต้นเป็น `2026-12-13` = **104 วัน** ไม่ใช่ 68
3. **ข้อ 100 ต้องส่งรูป (vision input)** — ไม่ได้นับเลยแม้แต่โทเคนเดียว

**ช่วงที่ควรวางงบ: $15-45 (ราว 500-1,600 บาท)** ยังถูกกว่าค่าสอบหนึ่งรอบ (1,500-2,500 บาท ตาม CLAUDE.md §6) → **อย่าลดรุ่นโมเดลเพื่อประหยัด**

**ต้องทำ:** บันทึก `resp.usage.input_tokens` / `output_tokens` ทุกครั้ง (เพิ่มคอลัมน์ใน `WritingFeedback` หรือตารางแยก) หลังตรวจจริง 10 ครั้งแรกให้เอาตัวเลขจริงมาคูณใหม่ **ตัวเลขในสเปกนี้ยังเป็นการประมาณ**

**อย่าทำ:** อย่าเปิด prompt caching (เรียกวันละ ~4 ครั้งกระจายทั้งวัน แคช 5 นาทีไม่มีวันโดน แต่จ่าย write แพงขึ้น 1.25 เท่าทุกครั้ง) · อย่าใช้ Batch API (ลด 50% จริง แต่ต้องรอผลข้ามคืน ทำลาย UX)

- **ห้าม raise ออกไปหา view** คืน `GradeResult` เสมอ หน้าเว็บต้องไม่ 500
- **ห้าม log ตัวงานเขียน** — `Dockerfile:31-32` ส่ง log ออก stdout ให้แพลตฟอร์มเก็บ ซึ่งเป็นบุคคลที่สาม log แค่ `request_id` + จำนวนโทเคน
- ทุกสาขาต้องบอก **“งานเขียนถูกบันทึกไว้แล้ว”** ซึ่งจริงได้ต่อเมื่อ `save()` เสร็จ **ก่อน** ยิง API
- ตรรกะ API อยู่ไฟล์นี้ไฟล์เดียว ห้ามกระจายเข้า view (CLAUDE.md §11)

**การรัน:** ยิง API ใน `threading.Thread` แล้วเขียนผลลง `WritingFeedback` ให้ HTMX poll — เลี่ยง timeout ทั้งหมดโดยไม่ต้องเพิ่ม Celery/Redis (ขัด D3) ข้อเสียคือ worker restart กลางคันผลหาย จึงต้องมีปุ่ม “ตรวจใหม่”

⚠️ **ยังไม่ได้ยืนยันด้วยตัวเอง:** ชื่อคลาสข้อยกเว้น เวอร์ชัน `anthropic==1.2.0` และ `client.messages.parse(output_format=PydanticClass)` มาจากรายงานของวิศวกรผู้ต่อ API ซึ่งอ้าง source ของ SDK และหน้า errors — **ก่อนเขียนโค้ดจริงต้องโหลด skill `claude-api` แล้วยืนยันซ้ำ อย่าลอกจากสเปกนี้โดยตรง**

## 1.9 เทสต์ที่ต้องมี (`core/tests/`)

- `char_count` นับ 汉字 ถูก ไม่นับตัวเลข/ตัวอักษรละติน/เครื่องหมายวรรคตอน
- band: ว่าง → `zero` · ข้อ 99 ใช้คำ 4/5 → `low` · `typo_count == 3` → `low` · `typo_count == 2` + coherent → `mid` · ครบทุกอย่างแต่ `char_count == 40` → `mid` **ไม่ใช่ `high`** (บั๊ก 1) · ครบทุกอย่าง 96 字 → `high`
- issue ที่ `certainty == "unsure"` ไม่ถูกนับในชั้น 3
- ไม่มี API key → `grade()` คืน `ok=False` ไม่ raise
- `source_type == "official_past_paper"` → ปฏิเสธก่อนยิง API (mock client ต้องไม่ถูกเรียกเลย)
- ผู้เรียนไม่ opt-in → ไม่ยิง API
- accept คำแย้ง 1 จุด → band คำนวณใหม่และเปลี่ยนจริง

## 2.3 กฎที่ **ห้ามแตะ** — พร้อมเหตุผล

**1. 三声 sandhi (66 คำในคลัง เช่น 处理 老板 展览 保险 领导 管理) — ห้ามแตะเด็ดขาด**
- บังคับใน**การออกเสียง** 100% แต่ธรรมเนียม**การเขียน**ตรงกันหมดทุกแหล่งว่า **ไม่เขียน**
- ผมตรวจไฟล์ต้นทางเอง: `处理 chǔlǐ` · `展览 zhǎnlǎn` · `老板 lǎobǎn` — ไม่มีการใส่ sandhi แม้แต่คำเดียว และผลเทียบทั้งคลังพบ **ต่างกัน 0 คำ** ในกลุ่มนี้
- CC-CEDICT ระบุตรงๆ ว่า “Tone sandhi is not indicated” (`http://cc-cedict.org/wiki/syntax`)
- เหตุผลเชิงหลักการ: sandhi เสียง 3 ขึ้นกับ**โครงสร้างวลี** ไม่ใช่ขึ้นกับคำ — 我很好 จัดกลุ่มได้ทั้ง `[wǒ][hén hǎo]` และ `[wó hén hǎo]` ตามจังหวะการพูด (`https://www.isca-archive.org/speechprosody_2012/li12d_speechprosody.pdf`) การเก็บลงคอลัมน์ของคำจึงผิดโดยนิยาม
- ผู้แย้งพยายามหาแหล่งที่ขัดแย้งข้อนี้แล้ว **หาไม่เจอ**

**2. กฎ 七/八 — ห้ามใส่** สูตรท่องจำเก่า “一七八不” เลิกใช้ในผู่ทงฮว่าปัจจุบัน และ GB/T 16159-2012 §6.5.2 ระบุเฉพาะ 一 กับ 不 ไม่พูดถึง 七/八 เลย ในคลังมี `七 qī` `八 bā` อย่างละคำ ปล่อยไว้

**3. 不 เสียงเบา (差不多 chàbuduō ฯลฯ) — ถูกอยู่แล้ว** CC-CEDICT มาร์ค `bu5` ให้ และตรงกับต้นทาง

**4. เสียงเบา 轻声 10 คำ — ห้ามแก้รวดเดียวในงานนี้ ต้องให้ครูตัดสิน**
คำที่ต่างจากต้นทางเรื่องเสียงเบา: `秘书 mìshū/mìshu` · `佩服 pèifú/pèifu` · `学问 xuéwèn/xuéwen` · `打交道 dǎjiāodào/dǎ jiāodao` · `痛快 tòngkuài/tòngkuai` · `已经 yǐjīng/yǐjing` · `知道 zhīdào/zhīdao` · `父亲 fùqīn/fùqin` · `母亲 mǔqīn/mǔqin` · `受不了 shòubùliǎo/shòu bu liǎo`
เหตุผล: `已经 yǐjīng` (现代汉语词典) กับ `yǐjing` (ลิสต์ HSK) **ถูกทั้งคู่** เป็นคนละธรรมเนียม ไม่ใช่ข้อผิด → **แยกเป็นงานคนละงาน ส่งให้ครูตรวจ**

**หลักฐานว่า pypinyin ทำพัง 81% (รันซ้ำสองบทบาทได้ตรงกัน):** มันเปลี่ยน 26 คำ โดย 21 คำเป็น 三声 ซึ่งห้ามเขียน และผลไม่สม่ำเสมอเพราะขึ้นกับพจนานุกรมวลีของมัน — `seg('处理')=['处理']` จึงถูกแตะ แต่ `seg('管理')=['管','理']` จึงไม่ถูกแตะ → ได้ `处理 chúlǐ` คู่กับ `管理 guǎnlǐ` ในคลังเดียวกัน และ 14 ใน 21 คำนั้นสร้างพยางค์ที่ชนกับเสียงจริงของอักษรอื่นในคลังนี้เอง (`大使馆 → dàshíguǎn` ชนกับ 时/实/食) ซึ่งคือความผิดพลาดคลาสเดียวกับกรณี 事物/食物 ที่ `data/vocab/QUALITY_REPORT.md §4` เคยจับได้ว่า “เป็นจุดตัดสินในพาร์ทฟัง”

**ถ้าเขียนกฎเองต้องระวังกับดัก 3 ข้อ (ทดสอบแล้วเกิดจริง):**
- แมตช์ที่ **ตัวอักษร 一/不 ไม่ใช่พยางค์ yi/bu** ไม่งั้นพัง 4 คำทันที: 依然 → `yìrán` ✗ · 医生 → `yìshēng` ✗ · 医院 → `yíyuàn` ✗ · 步骤 → `búzhòu` ✗
- เช็ค `len(hanzi) == len(syllables)` ก่อนเสมอ ไม่งั้นคำที่มี 儿 จับคู่ index ผิดตำแหน่ง
- ห้ามแตะเมื่อเสียงตั้งต้นเป็นเสียงเบา

**วิธีกันของสเปกนี้ (lookup) — 4 ชั้น:**
1. **ไม่มีการคำนวณเลย** — อ่านค่าจากไฟล์ที่คนทำไว้ ความเสี่ยงเชิงตรรกะ = 0
2. **whitelist 13 คำ** เขียนตรงในไฟล์ management command ไม่ใช่รันทั้งคลัง — ถ้าไฟล์ต้นทางเปลี่ยน คำอื่นไม่โดนกระทบ
3. **เขียนคอลัมน์ใหม่ ไม่ทับของเดิม** — `core/models/lexicon.py:43` `pinyin` คงเดิมทุกคำ
4. **`--dry-run` เป็นค่าตั้งต้น** ต้องพิมพ์ `--apply` ถึงจะเขียนจริง และพิมพ์ตาราง before/after ทุกคำก่อนเขียน

**สิ่งที่ห้ามทำแน่นอน:** อย่ารัน pypinyin ทับทั้งฐานไม่ว่ากรณีใด — คอลัมน์ `pinyin` ปัจจุบันเท่ากับผล pypinyin แบบไม่ sandhi อยู่แล้ว 2,178/2,206 การรันซ้ำไม่ได้อะไรเพิ่ม แต่จะย้อนงานแก้มือ (เช่น `告诉 gàosu` → `gàosù` ซึ่ง QUALITY_REPORT §3 ตัดสินแล้วว่าผิด)
